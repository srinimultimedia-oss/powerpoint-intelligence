# easySetup deployment workflow — 1 November 2026

Owner selected a single self-contained EXE covering x86/x64 Office and inclusion of existing local template assets for licensed computers only. The new easySetup folder contains the packager, compiled bootstrapper source, source/assets freshness checks, optional edit watcher and generated README workflow. No third-party installer framework or new download is required.

Signed Release builds call Build-EasySetup.ps1 after Build. Internal payload builds set PpiEasySetupBuild=true and suppress recursion. The packager builds both signed VSTO architectures with a portable relative template configuration, requires every template to appear in the application manifest, includes only deployment files and template assets, and signs the EXE with the selected code-signing certificate. It refuses publication on source changes or invalid signature/trust status. Build version increments from the existing deployment versions; the installer fingerprint covers plugin source, packaging source and template asset hashes.

The bootstrapper checks .NET 4.8, detects Office architecture from its PE header (not OS bitness), checks the installed VSTO runtime, refuses to close user presentations, verifies the embedded ZIP and individual file hashes, and uses versioned per-user extraction. It never alters trust stores or antivirus settings. Subsequent easySetup versions use normal VSTO uninstall/install and attempt rollback on failure. Migration from an older repository-based deployment can require one normal uninstall if ClickOnce refuses a changed deployment URL. A failed rollback is reported in the local setup log. No rollback success is claimed without execution.

Validation: eight pure path/hash assertions and packaging PowerShell parsing pass. Real production source compiles for x86 and x64 using compile-only targets, and both copy 62 template packages. Initial attempts to use Build without signing were correctly rejected by VSTO; this was not bypassed to produce an unsigned distributable. The actual signed build stops at certificate discovery in the AppContainer session. See artifacts/easySetup-first-build.log. No distributable EXE or install/upgrade acceptance is claimed. Desktop build with a usable trusted signing certificate, signed template-manifest coverage, actual installation, upgrade/rollback/uninstall and ribbon smoke testing remain required.

Every successful package regenerates easySetup/README.md and build.json. Signed Release builds automatically refresh the package; edit-time automatic rebuilding requires the watcher to remain running. Failed builds leave a prior package potentially stale; Test-EasySetup.ps1 rejects a source/hash mismatch. Do not present a prior executable as current after a failed build.
